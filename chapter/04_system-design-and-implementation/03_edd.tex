\subsection{Implementation Procedure}
\label{sec:evaluation-driven-development}

The prototype was developed using the Evaluation-Driven Development (EDD) approach (see
\autoref{sec:evaluation-driven-development}). Automated testing procedures were used even during
implementation to continuously evaluate the system.

User studies, human-in-the-loop evaluations, or expert assessments were not feasible during this early
prototyping and development phase, as such methods cannot be scaled without significant effort and have a
significan over head for testing basic functionality.
Instead, the system was further developed in short cycles consisting of implementation, testing, and adaptation.
This iterative approach is well-established in software development (see
\cite[p.~8]{ottAppsEffektivManagen2019}) and is particularly relevant for the EDD of AI-based systems, since
a complete test oracle cannot be assumed here due to the wide range of possible use cases
\cite[p.~39]{istqbrISTQBCertifiedTester}.

For components that did not rely on probabilistic AI model outputs, as well as unit and integration tests,
traditional software testing methods were used, since it was possible to define a clear and deterministically
verifiable test oracle for them. However, since the vast majority of the system under test relied on
LLM-based components and was therefore probabilistic, this was not possible in most cases.

For this reason, an approach inspired by the “LLM-as-a-Judge” method was chosen (see
\autoref{sec:llm-as-a-judge}). In the version used here, the LLM did not evaluate the output in
real time, but was used to generate scenarios (mostly possible conversations) in advance for specific meeting
situations in order to create a lexical test oracle. This was used as part of code-based (see
\autoref{sec:code-based-testing}) automated testing, in combination with regular expressions.
The oracle generated by the LLM-Judge operationalized which formulations a professionally appropriate
facilitator statement must include in the respective scenario and which it must not include. The output of
the individual components was monitored and analyzed to better understand and evaluate the behavior of the
components in the various scenarios.

It should therefore be emphasized once again that, during development, the system was not exposed to any live
meeting situations, but rather to synthetic data simulating potential brief interactions that might occur in a meeting.

During development, the system was continuously tested in unstructured, exploratory tests, both individually
and, on an irregular basis, with multiple participants in various, unspecified scenarios. The goal was to
develop a sense of the system’s behavior even before the actual user studies (see
\autoref{ch:empirical-prototype-validation}). This was intended to identify obvious errors as well as
critical vulnerabilities where the system deviates from its intended behavior at an early stage, so that the
system could be adjusted.

\subsection{Limitierungen des Vorgehens}
\label{sec:edd-limitations}

A lexical oracle is incomplete, and in this case, its quality depends on the dialogs generated by the LLM.
A valid facilitator utterance can demonstrate the intended behavior without containing the specified phrases;
conversely, a match may be formally correct but contextually inappropriate.
Furthermore, isolated dialogs obscure the dynamics of a real meeting: turn-taking, timing, and the group’s
reaction to an intervention are not taken into account.
Which scenarios were included as test data in the first place also depends on the errors observed during the
exploratory phase and is thus selected by the authors.
Nevertheless, this combination—of continuous, oracle-based testing during implementation and independent
human-in-the-loop evaluation afterward (through user studies)—constitutes a valid approach for testing
LLM-based agentic systems. \cite[pp.~6--7]{mohammadiEvaluationBenchmarkingLLM2025}.
